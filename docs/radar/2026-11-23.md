## Trial (promising, needs a spike)

### Isthmus: keep one-step samples calibrated (https://arxiv.org/abs/2611.23616)
- What: A no-cost change to how flow-map/MeanFlow training samples (start, end) time pairs. It puts 5% of pairs on the triangle edge that joins the one-step pair to the diagonal, and the authors report that this stops one-step samples collapsing toward the conditional mean.
- Fit: MeanFlow PDE / the (r, t) pair sampler in the training loss. Last week's digest named the loss as `training/loss.py`; it was not re-read this run. The paper's diagnosis is aimed at the brief's exact setup: "supervising the one-step jump directly makes this worse," which is what endpoint-MSE training does. Ensemble spread then feeds the Energy Score stage and its q90/q95 intervals.
- Evidence: arXiv:2611.23616, submitted 17 Nov 2026 (cs.CV; arXiv non-exclusive license; no code link on the abstract page). The network, loss and inference code are unchanged. On brain-MRI posterior sampling, the authors report one-step calibration restored to 0.96 and correlation with multi-step samples of 0.93, with less seed variance. Tasks were MRI reconstruction, face inpainting, and CIFAR-10 / ImageNet-32 generation. Not tested on PDEs.
- Experiment: in a **new directory outside** `masked-joint-mean-flows-pde/`, fork the pair sampler so 5% of pairs lie on that edge. On one small PDE pair task and a laptop or single-GPU budget (no ALCF), compare K-sample ensemble spread, Energy Score and empirical q90 coverage against the unmodified sampler under the same seeds. Stop if spread does not move.
- Effort: S–M (sampler change is S; evaluation on existing tooling is M).

### Add blink-multilingual-64M to the embedding A/B, updated (https://huggingface.co/minishlab/blink-multilingual-64M)
- What: A static (model2vec) embedder with no transformer forward pass. It is a third arm in last week's "wire `LATTICE_EMBEDDING_MODEL`" trial, as the cheapest laptop option.
- Fit: Lattice / `packages/core/lattice/retrieval/vector_store.py` and `packages/core/lattice/config.py` (`embedding_model`, `.env.example` `LATTICE_EMBEDDING_MODEL=all-MiniLM-L6-v2`).
- Evidence: HF card created 17 Nov 2026, MIT. 64.0M parameters (a 250k×256 table, 256 MB fp32). On MTEB(Multilingual, v2), 131 tasks, the card reports a 51.60 task mean and 47.52 on Retrieval at 256-d, the best mean among the static models it compares. The card does not compare it with MiniLM or transformer embedders. It loads via `sentence_transformers.SentenceTransformer`, which Lattice already depends on, or via `model2vec` 0.10.0 (MIT; core deps are numpy/safetensors/tokenizers, no torch). Also relevant: arXiv:2611.20702 (16 Nov) finds that index-reuse tricks never avoid re-encoding when the embedding model changes. For Lattice's small corpora, just re-ingest.
- Experiment: once the setting is wired, run the same 20-query recall@10 on `examples/aerospace` for `all-MiniLM-L6-v2`, `minishlab/blink-multilingual-64M` and (optionally) `microsoft/harrier-oss-v1-270m`. Record ingest wall-clock on CPU. Adopt blink only if recall is within ~2 points of MiniLM and ingest is clearly faster.
- Effort: S once the embedding wiring exists (the wiring itself is M, per last week).

### GLiNER2 2.2.0 and Cognee's production recipe for the GLiNER extractor, updated (https://github.com/fastino-ai/GLiNER2/releases/tag/v2.2.0)
- What: Two changes to last week's GLiNER2.5 extractor trial: a library release that fixes problems Lattice would hit, and a public write-up of two heuristics that made GLiNER usable for KG extraction.
- Fit: Lattice / `packages/core/lattice/graph/extractor.py` and `builder.py`; HANDOFF item 4 (cleaner spans before merge).
- Evidence:
  - `gliner2` 2.2.0 was released 20 Nov 2026 (Apache-2.0). It fixes OOM on large relation schemas (#195) and keeps JointIE relation descriptions (#204). Fastino's own release notes list 12 known test failures (numeric drift, loading-test updates, CUDA-only checks), so pin the version and run the spike on CPU/MPS.

It also claims about 30× faster per chunk than an *estimated* LLM baseline in Cognee's internal evaluation; that figure is not independently verified. Cognee's docs say the open-source extractor is a demo of an enterprise-licensed version, so borrow the ideas, not the code.

### Inkling 2 Mini as an optional local agent model (https://huggingface.co/thinkingmachines/Inkling-2-Mini)
- What: An open-weights Thinking Machines model with tool use and a 1M-token context, served by Ollama as `inkling-2-mini`. It is a candidate "quality" local model for the agent team instead of the `llama3.2` default.
- Fit: Lattice / `.env.example` `LATTICE_OLLAMA_MODEL` and `packages/core/lattice/agents` (planner/researcher/writer/reviewer). It relates to HANDOFF item 3: a stronger local reviewer and writer should hit `max_iterations` with a rejected review less often. That changes the symptom, not the status bug, which still needs fixing.
- Evidence: the card lists release date 20 Nov 2026, Apache-2.0, 26.4B total / 5.4B effective active parameters, and a ~20 GB checkpoint. It recommends **Apple silicon with ≥32 GB memory**. The Ollama library page lists a 20 GB tag. Vendor-reported scores include MCP Atlas 82.7% (Qwen3.8-27B: 77.3%), AA-Omniscience non-hallucination 63.4% (Qwen3.8-27B: 71.4%) and LongBench v2 66.9%; none are independently verified. Cost is the catch: on a 16 GB laptop it will not fit, so it can never be the default.
- Experiment: with `LATTICE_OLLAMA_MODEL=inkling-2-mini`, run `lattice eval` and the aerospace `lattice run` prompts. Compare with `llama3.2` on completion rate, review iterations used, and wall-clock per task. Because item 7 means eval doesn't exercise retrieval yet, treat this as an agent-loop comparison only.
- Effort: S (config only), if the owner's Mac has ≥32 GB.
